# OMP Remote v0.1.0 Verification

Date: 2026-08-22

This record covers the prepared source release. It does not authorize repository visibility changes, tags, published releases, npm publication, or claims of physical mobile notification delivery.

## Source validation

The complete workspace validation passed on macOS arm64 with Node 24.19.0 and pnpm 11.17.0:

```bash
pnpm install --frozen-lockfile
pnpm format:check
pnpm lint
pnpm lint:lines
pnpm typecheck
pnpm test
pnpm build
```

Results:

- Formatting: 245 files checked, no changes required.
- Lint: zero errors; 125 existing warnings and 23 existing informational diagnostics.
- File length: every tracked source file remained within 1,000 lines.
- Typecheck: 15 of 15 workspace tasks passed.
- Root script tests: 48 passed after the verification changes.
- Workspace tests: protocol 184, observability 6, OMP RPC 9, OMP extension 34, session client 93, UI 5, sessions 378, web 89, and daemon 273 passed.
- Build: all nine workspace build tasks passed; the production PWA generated its manifest, service worker, and precache.

The final verification branch was cloned through authenticated Git into a path containing spaces, brackets, and a semicolon. That clean clone passed the frozen install, format, lint, file-length, typecheck, test, and build sequence above.

## Setup matrix

### macOS

An isolated HOME, generated service files, and command fixtures were used so setup did not replace the workstation's launch agent or OMP extension. Setup passed twice consecutively. The generated launchd plist:

- used the selected checkout's absolute path;
- preserved its PATH with XML escaping;
- persisted the configured loopback host and port; and
- pointed logs into the isolated HOME.

On both runs, a launchctl fixture observed bootout and bootstrap of the same generated definition. A separately supervised real daemon at the configured endpoint supplied the health response. This verified idempotent command sequencing, rendering, and readiness behavior without loading a real workstation service.

### Linux

An Ubuntu 24.04 arm64 container used Node 24.19.0, pnpm 11.17.0, an isolated HOME, and a checkout named `OMP Remote [linux]; verify`. Setup completed from a clean dependency install and build. The generated systemd user unit preserved the unusual absolute path and configured endpoint. The observed command order was:

1. `systemctl --user daemon-reload`
2. `systemctl --user enable omp-remote.service`
3. `systemctl --user restart omp-remote.service`

The container used command fixtures for `systemctl` and Tailscale plus a separately supervised real built daemon for the readiness response. This verified generated-unit rendering, systemctl command sequencing, the real-daemon readiness gate, and Serve target resolution. It did not restart a real systemd user service or change a real Tailscale mapping.

## Failure behavior

- Node 22.23.2 stopped immediately with the required `24.18.0 or newer` message.
- Wrong or malformed pnpm and OMP versions stopped before installation.
- Missing OMP and Tailscale commands retained clear prerequisite errors and stopped subsequent stages.
- An occupied health endpoint identifying as another service stopped setup before Tailscale Serve.
- An unhealthy OMP Remote endpoint timed out instead of being treated as ready.
- Invalid loopback host or port overrides were rejected.
- Real RPC session launch from the isolated browser HOME reached OMP and failed visibly because that HOME had no configured model or authentication. No live model response is claimed from that environment.

## Runtime browser flow

Chromium exercised the current dashboard against the daemon and a deterministic extension-protocol fixture:

- an idle terminal session registered and appeared;
- a prompt entered the transcript and changed the session to running;
- the active-run composer sent `steer`, not `follow_up`, and the steered text appeared;
- abort required confirmation and returned the session to idle;
- reload reconnected to the selected session and retained its transcript;
- a native-shaped rich Ask appeared, accepted `SQLite`, and returned the complete structured response to the extension socket.

The production daemon served an installable PWA surface with `/manifest.webmanifest`, an active service-worker controller, and the generated offline assets.

## Notification lifecycle

Chromium exercised the production notification settings with browser notification permission granted. Because the automation Chromium does not provide a usable external push-service registration, a deterministic standards-shaped `PushSubscription` replaced only that external browser boundary. The application, WebSocket/API, daemon store, local preference, update, and cleanup paths remained real.

Observed state transitions:

1. both event preferences disabled;
2. **Input required** enabled and a device registration persisted;
3. **Session idle** enabled on the same device registration;
4. **Input required** disabled while the subscription remained active;
5. **Session idle** disabled, the subscription unsubscribed, local registration cleared, and the daemon retained zero devices.

This is not evidence of delivery through Apple, Google, or another browser push service. Real delivery of both event types to installed current iOS/iPadOS Safari and Android Chrome PWAs remains an explicit publication gate.
